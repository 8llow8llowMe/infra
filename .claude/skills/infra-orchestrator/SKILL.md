# Infra orchestrator

이 저장소의 커밋은 운영에 바로 적용되지 않는다. 사고는 **커밋할 때가 아니라 호스트에 반영할 때** 난다. 그래서 이 절차의 무게는 실측과 적용 단계에 있다.
배치 · 포트의 정본은 루트 `README.md`, 저장소 동작 방식과 호스트 함정은 `CLAUDE.md` 다. 이 문서는 순서만 정한다.

## 1. 분류

| 유형 | 대상 | 예 |
| --- | --- | --- |
| `DOCS` | 문서 · 템플릿 · 스킬만 | README 실측값 갱신 |
| `CONFIG` | 파일만 바뀌고 다음 재생성 때 적용되는 설정 | compose 로그 상한, `.env.example` 변수 추가 |
| `RECREATE` | 컨테이너 재생성 · 재빌드 · `docker update` 가 필요한 변경 | 자원 상한, 이미지 버전, fail2ban 설정 |
| `INGRESS` | storage(`.12`) nginx · certbot · fail2ban, 도메인 · DNS | 새 도메인, conf 수정, 공인 IP 변경 |
| `CROSS_HOST` | 여러 호스트에 걸친 변경, 서비스 이동, 노드 추가 · 제거 | Jenkins 에이전트 이동, Prometheus 대상 추가 |
| `INCIDENT` | 장애 · 이상 징후 대응 | 응답 불능, OOM, 인증서 오류 |

## 2. 위험 등급

| 등급 | 의미 | 기본 깊이 |
| --- | --- | --- |
| `R0` | 호스트 반영 없음(`DOCS`) | 로컬 검사 → PR |
| `R1` | 한 호스트 · 한 컴포넌트, 무중단 또는 영향이 dev 한정 | 실측 → 백업 → 적용 → 확인 |
| `R2` | 짧은 중단이 있거나 공유 컴포넌트 | R1 + 적용 순서 · 복구 명령을 미리 적고, 빌드 · 사용량이 없는 시점에 적용 |
| `R3` | 아래 신호가 **2개 이상** | R2 + 사용자에게 계획을 먼저 보이고 확인받은 뒤 적용 |

위험 신호:

- 전 도메인 인그레스(storage nginx) — conf 하나가 깨지면 모든 사이트가 내려간다
- 운영(prod) 트래픽 경로
- Vault(재생성하면 sealed), 시크릿 · 토큰 · agent secret
- 데이터 볼륨 · DB · Kafka · Redis 데이터
- `ollama-01` 자원 예산(`ollama/HOST-STABILITY.md` 합계)
- Jenkins controller · 공유 빌더(진행 중 빌드)
- 공인 IP · DNS · 포트포워딩 · fail2ban(나를 차단할 수 있음)
- 되돌리는 방법이 확인되지 않음
- 원인 미상(`INCIDENT`)

## 3. 실측 (읽기 전용)

`DOCS` 가 아니면 **먼저 호스트를 본다.** 레포가 항상 정본은 아니다.

- `cd ~/infra && git status --short` — 호스트별 의도된 차이(루트 README 2절 표)와 서버에서 먼저 고친 파일을 구분한다.
- 바꿀 파일은 서버 판과 레포 판을 diff 한다. 주석 · 공백을 뺀 **기능 차이**가 있으면 어느 쪽이 앞선 것인지 판단하고, 서버가 앞섰으면 서버 판을 레포로 올리는 것부터 한다.
- 실제 실행 상태: `docker ps`, `docker inspect`(마운트 · 상한 · env), `free -h`, 관련 로그. compose 파일과 실제 컨테이너가 다를 수 있다(예: controller 는 옛 compose 로 떠 있음).
- 바인드 마운트를 확인한다. **디렉터리째 마운트된 곳에 파일을 더하면 즉시 반영된다**(storage `nginx/conf.d`).
- 접속 · 실행에 시크릿이 필요하면 값은 출력하지 않는다. `docker compose config` 출력도 시크릿이 풀려 있으니 공유하지 않는다.

여러 호스트 · 여러 파일을 훑어야 하면 하위 에이전트(읽기 전용 탐색)를 쓸 수 있다. 질문과 호스트 · 경로를 좁혀 넘기고 요약만 받는다.

## 4. 계획

`R1` 이상은 적용 전에 아래를 고정한다. `R3` 는 이 계획을 사용자에게 보이고 확인받는다.

1. 바꿀 파일과 호스트, 적용 방법(`git pull` 만 / `up -d` / `up -d --build` / `docker update` / `nginx -s reload`)
2. 백업: `~/backups/infra-<YYYYMMDD>/` 에 바뀔 파일과 `.env` 를 먼저 묶는다(`tar czf`)
3. 적용 순서와 예상 중단(어느 서비스가 몇 초 · 몇 분)
4. 확인 명령과 정상 기준
5. 복구 명령(백업 풀기 · 이전 이미지 · 이전 상한)

컴포넌트별 반영 방법은 `CLAUDE.md` "반영 방식이 컴포넌트마다 다른 곳"을 따른다. 특히:

- fail2ban 설정은 이미지에 COPY 되므로 `up -d --build`.
- ollama compose 를 직접 올리면 `.env` 의 `AMD_GPU_RENDER_GROUP` 이 있어야 한다.
- `.env.example` 에 변수를 더해도 운영 `.env` 에는 들어가지 않는다. 호스트 `.env` 수동 병합을 계획에 넣는다.
- 상한만 바꿀 땐 재시작 없는 `docker update` 를 먼저 검토한다.

## 5. 로컬 검사

작업 PC 에는 Docker 와 호스트 `.env` 가 없다.

```bash
bash -n <script>.sh          # 또는 sh -n
git diff --check
```

- YAML 은 파싱까지만 로컬에서 확인한다. `docker compose ... config -q` 는 **대상 호스트에서** 임시 디렉터리 · 더미 시크릿으로 돌리고 지운다.
- nginx conf 는 storage 에서 `docker exec nginx nginx -t` 로만 확인할 수 있다.

## 6. 적용 (호스트별)

- 한 번에 한 호스트 · 한 컴포넌트. 앞 단계 확인이 끝나야 다음으로 간다.
- 백업 → 적용 → 확인. 파일은 inode 를 지키도록 `cat > file` 로 덮는다(파일 단위 바인드 마운트 대비).
- **storage nginx:** 파일을 바꾸거나 `git pull` · checkout 한 직후 `nginx -t` 를 먼저 돌리고, 통과할 때만 reload 한다(`nginx -t && nginx -s reload`). 새 conf 가 들어오면 그 도메인의 인증서 파일이 있는지 본다.
- 인그레스를 바꿨으면 영향 도메인의 HTTPS 응답과 SNI 인증서를 확인한다.
- 재생성은 진행 중인 Jenkins 빌드 · Ollama 요청이 없는 시점에 한다.
- 예상과 다른 결과가 나오면 **멈추고 복구부터** 한다. 고치면서 앞으로 나가지 않는다.
- 적용 중 생긴 중단은 시간 · 영향 범위 · 원인 · 복구를 기록해 PR 과 보고에 적는다.

## 7. PR

- 이슈 → 브랜치(`<type>/infra/<이슈번호>-<slug>`) → 커밋(`[INFRA] type: 요약 (#번호)`) → PR(base `main`). 이슈 · PR 작성은 `issue` · `pr` 스킬을 따른다.
- 경로를 하나씩 스테이징한다. 호스트에서 가져온 파일에 시크릿 · 실IP 외 민감값이 없는지 본다(공개 저장소).
- PR 의 "적용 및 복구"에 **이미 적용했는지, 머지 뒤 적용할지**를 분명히 적는다. 실행하지 못한 검증은 체크하지 않고 이유를 적는다.
- 운영 사실이 바뀌었으면 같은 PR 에서 루트 README · 컴포넌트 README(날짜 붙인 실측값)와 `CLAUDE.md` 를 고친다.

## 8. 머지 뒤

1. 각 호스트 `~/infra` 를 머지된 `main` 으로 맞춘다. 로컬 변경 · 미추적 파일 때문에 `git pull` 이 막히면, 바뀔 파일을 백업한 뒤 `git reset --mixed origin/main` 하고 **바뀐 파일만** 반영한다(작업 트리가 옛 판과 같으면 새 판으로, 이미 새 판이면 그대로, 둘 다 아니면 남기고 보고).
2. storage 는 1번 직후 `nginx -t`.
3. 이슈 체크박스를 실제 완료 항목만 체크한다. 남은 일(사용자 작업 · 후속)이 있으면 댓글로 적고 열어 둔다. 끝났으면 결정 사항을 댓글에 남기고 닫는다.
4. 워크트리 · 로컬 브랜치를 지운다(원격 브랜치는 머지 때 삭제됨). 지우기 전 `git status` 가 깨끗한지 본다.

## 완료 조건

1. 요청한 변경이 레포와 대상 호스트에 반영되었고, 확인 명령을 실제로 돌렸다.
2. 백업 위치와 복구 방법이 PR 에 있다.
3. 호스트 `git status` 에 표에 없는 차이가 없다.
4. 보고에 유형 · 등급(R3 면 해당 신호), 바뀐 호스트, 실행한 확인, 중단 기록, 남은 일이 있다.
